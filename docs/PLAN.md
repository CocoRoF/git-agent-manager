# git-agent-manager 설계와 계획

근거 자료는 [RESEARCH.md](RESEARCH.md). 진행 상황은 이 저장소의 Milestones 와 Issues 가 원본이다.

## 1. 정의

한 번 연결하면, 저장소를 다루는 에이전트(Claude, GPT, 무엇이든)가 마일스톤과 계획을 따라 일하고, 진행 상황이 HTML 대시보드에 저절로 나타난다.

**막기보다 따르기가 더 쉽게 만든다.** 계획대로 일하는 길이 가장 편하고, 벗어난 일은 막지 못해도 반드시 보인다.

## 2. 첫 번째 원칙: 사용자에게 새것을 늘리지 않는다

개인 사용자가 쓰게 하려면 배울 것, 저장소에 생기는 것, 나중에 치울 것이 거의 없어야 한다.

- **마일스톤은 GitHub Milestone 이고 작업은 GitHub Issue 다.** 새 파일 형식, 새 브랜치, 새 DB, 새 계정이 없다.
- **이미 쓰던 저장소가 바로 대상이 된다.** 마일스톤과 이슈가 있으면 곧장 대시보드가 나오고 에이전트가 따른다.
- **상태는 저장하지 않고 계산한다.** 따로 적어 두는 값이 없으니 어긋날 일도 없다.
- **사람은 늘 쓰던 화면에서 끼어든다.** 휴대폰으로 이슈에 댓글을 달거나 순서를 바꾸면 에이전트가 다음 호출에서 본다.
- **지워도 남는 것이 멀쩡하다.** 연결을 끊어도 평범한 마일스톤과 이슈만 남는다.

처음 검토한 전용 브랜치 안(`gam-state`)은 버렸다. 잠금 문제는 잘 풀지만, 브랜치 목록에 낯선 것이 생기고 계획이 사용자가 늘 보는 곳 밖에 있게 된다. 이슈를 쓰면 같은 문제를 더 단순하게 풀 수 있음을 시험으로 확인했다.

## 3. 설계

### 3.1 대응 관계

| 개념 | GitHub 에서 |
|---|---|
| 마일스톤과 완료 조건 | Milestone, 설명의 체크박스 |
| 작업 | 마일스톤에 속한 Issue |
| 작업의 완료 조건 | 이슈 본문의 체크박스 (GitHub 이 진행도를 그려 준다) |
| 선행 작업 | Issue dependencies (blocked by) |
| 안건 | `agenda` 라벨 Issue, 하위 작업은 sub-issue |
| 역할 | `role:*` 라벨 |
| 작업 잡기 | 이슈에 연결된 브랜치 `task/12-slug` 생성 |
| 진행 기록 | 이슈 댓글 하나를 계속 고쳐 씀 |
| 완료 | `Closes #12` PR 의 병합 |

### 3.2 상태는 사실에서 계산한다

| 상태 | 판정 |
|---|---|
| proposed | 열림, `proposed` 라벨 (승인 대기) |
| ready | 열림, 마일스톤 있음, 선행 작업 없음, 브랜치 없음 |
| blocked | 열린 선행 작업이 있거나 `blocked` 라벨 |
| in progress | `task/12-*` 브랜치 있음 |
| in review | 그 브랜치의 열린 PR 또는 `Closes #12` 열린 PR 있음 |
| done | 완료로 닫힘. PR 병합이면 증거 있음, 아니면 "증거: 댓글" 로 구분해 표시 |
| dropped | not planned 로 닫힘 |

마일스톤 진행률은 GitHub 의 닫힘/전체와 같은 수를 쓴다. 대시보드와 GitHub 화면의 숫자가 다를 일이 없다.

### 3.3 동시성

`POST git/refs` 와 `createLinkedBranch` 는 같은 이름에 대해 하나만 성공한다 (실제 GitHub 에서 20개·10개 동시 호출, 각각 1개 성공). **브랜치를 만드는 일 자체가 잠금이다.** 어차피 필요한 브랜치라 잠금 때문에 생기는 것이 없다.

- 신원: MCP 클라이언트 이름에 세션 표시를 붙인다 (`claude-code#a3f`). 설정이 필요 없다.
- 잡고 사라진 작업: 브랜치의 마지막 커밋과 진행 댓글이 일정 시간 멈추면 다른 에이전트가 **그 브랜치를 이어받는다.** 하던 일이 이어진다.

### 3.4 에이전트 접점: 도구 6개

CLI 와 MCP 는 같은 코어를 부른다.

| 도구 | 하는 일 |
|---|---|
| `gam_status` | 지금 마일스톤, 내 작업, 다음 할 일, 대시보드 주소 |
| `gam_plan` | 마일스톤과 작업 묶음 만들기·추가 |
| `gam_claim` | 다음 작업이나 지정 작업을 잠그고 완료 조건과 브랜치를 준다. `new` 를 주면 작은 작업을 바로 만들어 잡는다 |
| `gam_update` | 진행 한 줄 |
| `gam_finish` | 증거를 내고 PR 을 열거나, 코드 없는 일이면 닫는다 |
| `gam_block` | 막힘 알림, 사람에게 질문 |

모든 응답 끝에 `next:` 한 줄을 붙여 긴 지시문 없이 도구 응답으로 이끈다.

**작은 작업 경로가 중요하다.** 오타 하나에 계획 수정을 요구하면 에이전트는 우회한다. `gam_claim({new})` 한 번이면 이슈와 브랜치가 생기고 `unplanned` 라벨이 붙는다. 막지 않고 보이게 한다.

### 3.5 연결

```bash
npx git-agent-manager        # 이 한 줄
```

1. **기계 설정, 한 번만.** 깔려 있는 에이전트(Claude Code, Codex, Cursor, Gemini)를 찾아 사용자 수준 MCP 로 등록한다. 이후 **모든 저장소에서** 작동하고 저장소마다 설정할 것이 없다. 저장소는 작업 폴더의 `origin` 에서 알아낸다.
2. **토큰 없음.** `GITHUB_TOKEN`, `gh auth token`, `git credential` 순서로 이미 있는 것을 쓴다.
3. **저장소 표시, 선택.** README 표시와 워크플로 파일을 PR 하나로 제안한다.

마일스톤이 있는 저장소만 "계획이 있는 저장소" 다. 없으면 아무 말도 하지 않다가 큰 일을 할 때나 사용자가 원할 때 `gam_plan` 을 제안한다.

저장소에 들어갈 수 있는 파일은 다음이 전부이고, 전부 선택이다.

| 파일 | 왜 | 없으면 |
|---|---|---|
| README 표시 | 진행도 그림과 대시보드 링크 | Milestones 탭과 뷰어 주소로 본다 |
| `.github/workflows/gam.yml` | 병합 즉시 그림 갱신, PR 검사 | 다음 도구 호출 때 갱신 |
| `AGENTS.md` 포인터 몇 줄 (`--agents-md`) | 팀원·클라우드 에이전트까지 따르게 | 기계에 설정한 에이전트만 따른다 |
| `.github/gam.yml` | 기본값 변경 (승인 방식, 에이전트 병합) | 기본값 |

### 3.6 대시보드

레포마다 자기 대시보드를 그 레포의 GitHub Pages (또는 사용자 도메인) 에 둔다. 페이지에는 그 레포만 박혀 있고, 데이터는 브라우저가 GitHub API 에서 직접 읽는다.

- 서버가 없다. 레포가 이미 Pages 를 쓰고 있으면 건드리지 않고 `gam site` 로 다른 곳에 올린다.
- 볼 권한은 GitHub 권한 그대로다. 비공개 저장소의 계획이 새지 않는다.
- 공개 저장소는 로그인 없이 열린다. 비공개는 읽기 전용 토큰을 넣거나 `gam dashboard` 로 HTML 파일을 만들어 연다.
- 여러 저장소를 모으면 전사 현황판이 된다.

README 그림은 숨은 ref `refs/gam/status` 에 넣는다. 브랜치 목록에 안 보이고, 클론해도 받아지지 않으며, 한 커밋을 덮어쓰므로 역사가 쌓이지 않는다. `main` 에 봇 커밋이 생기지 않는다.

```
https://raw.githubusercontent.com/owner/repo/refs/gam/status/status.svg
```

비공개 저장소의 README 는 익명 이미지 요청이 불가능해 링크만 넣는다.

### 3.7 준수 사다리

| 단계 | 장치 | 범위 |
|---|---|---|
| 1 안내 | MCP 안내, `next:`, 선택적 AGENTS.md 포인터 | 어디서나 |
| 2 사후 감사 | 기본 브랜치의 커밋 중 작업에 연결되지 않은 것을 집계, 준수율 표시 | 어디서나 |
| 3 에이전트 훅 | 세션 시작 때 현황 주입, 잡은 작업 없이 수정하면 경고 | 에이전트별, 실패하면 통과 |
| 4 PR 검사 | 작업 연결, 선행 작업, 완료 조건 검사 | 어디서나 빨간불 |
| 5 합치기 차단 | 4를 필수 검사로 | 공개 저장소 또는 Pro 이상 |
| 6 런타임 통제 | 실행 환경이 턴을 직접 관리 | Aristoteles 처럼 런타임을 가진 곳 |

### 3.8 보안: 공개 저장소의 이슈는 남이 쓸 수 있다

이슈를 작업 목록으로 쓰면 낯선 사람이 "이걸 실행해" 라고 적어 에이전트를 조종하려 들 수 있다. 처음부터 막는다.

- **마일스톤이 있어야 작업이다.** 마일스톤 지정에는 triage 이상의 권한이 필요하므로 외부인이 작업을 만들 수 없다.
- **쓰기 권한자의 글만 지시로 넘긴다.** 작성자가 OWNER·MEMBER·COLLABORATOR 가 아닌 이슈는 잡을 수 없고, 그런 사람의 댓글은 응답에서 빼고 몇 개 있는지만 알린다. 그 내용을 쓰려면 권한자가 작업을 새로 쓴다.
- **도구 응답에서 이슈 내용을 데이터로 표시한다.**
- **뷰어는 모든 내용을 이스케이프하고** 엄격한 CSP 를 건다. 토큰은 읽기 전용만 안내한다.

### 3.9 다른 저장소 서비스와 Aristoteles

코어는 `Tracker` 인터페이스 뒤에 GitHub 구현을 둔다. GitLab, Gitea 도 이슈와 마일스톤이 있어 같은 모델이 맞는다. GitHub 이 없는 환경을 위한 로컬 구현은 Aristoteles 연동 때 판단한다.

Aristoteles 는 이 모듈을 먼저 제대로 완성한 뒤 적용한다. 런타임을 쥐고 있어 사다리의 6단계까지 쓸 수 있다.

### 3.10 기술

- TypeScript, 실행 의존성 없는 번들 하나. 같은 파일이 `npx`, MCP stdio, GitHub Action 으로 돈다. Node 20 이상.
- 하지 않는 것: 자체 DB, 필수 호스팅 서버, 에이전트 실행, 방법론 프롬프트 묶음, 양방향 동기화.

## 4. 단계

진행 상황의 원본은 이 저장소의 [Milestones](https://github.com/CocoRoF/git-agent-manager/milestones) 다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 0 설계 검증 | GitHub 동작 시험 | 끝. [RESEARCH.md](RESEARCH.md) |
| 1 코어와 CLI | 상태 계산, 잠금, 도구 6개, 보안 규칙 | 끝 |
| 2 MCP 와 연결 | MCP 서버, 한 줄 연결, README 표시 | 끝 |
| 3 대시보드 | 뷰어, HTML 파일, 여러 저장소 | 끝 |
| 4 준수 | 벤치마크, 사후 감사, 워크플로, 훅 | 끝. [BENCHMARK.md](BENCHMARK.md) |
| 5 안건과 다중 에이전트 | 안건, 역할, 승인, 겹침 경고, 에이전트 병합 | 끝 |
| 첫 배포 | npm 배포 | npm 계정이 필요하다 |
| 6 Aristoteles 적용 | 공간 도구, 현황 주입, 턴 종료 처리, 현황판 | 다음 |

설계에서 달라진 점:

- 편집마다 도는 훅은 넣지 않았다. 턴이 끝날 때 한 번 묻는 훅으로 바꿨다. 편집마다 도는 훅은 너무 느리다.
- 범위 경로를 선언하게 하지 않고, 브랜치가 실제로 바꾼 파일로 겹침을 알린다.
- 연결은 레포 단위다. 레포 폴더가 아니면 실행되지 않고, 기계 전역 설정은 건드리지 않는다. 레포에 `.mcp.json`, `.codex/config.toml`, `AGENTS.md` 안내를 PR 로 넣는다. MCP 안내문만으로는 Codex 가 도구를 거의 부르지 않았다.
- 대시보드는 레포마다 자기 것이다. 그 레포의 GitHub Pages 나 사용자 도메인에서 열리고, 페이지에 박힌 레포만 보여 준다. 하나의 공용 주소에서 아무 레포나 여는 방식은 버렸다.

## 5. 위험

| 위험 | 대응 |
|---|---|
| 에이전트가 도구를 안 부른다 | 벤치마크로 재고, 세션 훅과 사후 감사로 드러낸다 |
| 절차가 일보다 무겁다 | 작은 작업 경로, 작업 수 상한 경고 |
| 저장소에 이슈가 넘친다 | 작업 크기 안내, 필터 |
| 공개 저장소의 계획은 누구나 본다 | 연결 때 알리고, 민감한 내용을 이슈에 적지 말라고 안내 |
| 뷰어의 익명 한도 (시간당 60회) | ETag 로 호출을 줄이고, 소진되면 토큰을 안내 |
| GitHub 쓰기 API 한도 (분당 80회 정도) | 큰 계획은 천천히 만든다 |
